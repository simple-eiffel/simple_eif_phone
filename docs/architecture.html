The layers

 your app (Eiffel)
      |
 PHONE_CONTROLS     Android's own controls  (cluster src/controls)
   or SW_WINDOW     simple_widgets on cairo (cluster android_shell)
      |
 SIMPLE_EIF_PHONE   events, lifecycle, touches, screen, metrics, storage, assets, log
      |
 PHONE_NATIVE       the only class that calls C
      |
 runtime/c          sephone glue + Android's native_app_glue
      |
 Android            NativeActivity

Android has no C API for its controls, so runtime/c/sephone_controls.c makes and drives them through JNI. A control may be touched only on Android's UI thread, so Eiffel queues orders and the UI thread carries them out. Orders never wait for an answer: Android's UI thread blocks on the Eiffel thread during pause and resume, and a wait the other way would deadlock. What a control has to say comes back as an event.

NativeActivity takes the window's surface and input for itself. EifPhoneControlsActivity hands both back, so controls draw and receive touches, while the Eiffel thread and lifecycle events stay as they are.

The model classes (PHONE_LIFECYCLE, PHONE_TOUCHES, PHONE_EVENT) use no C, so their contracts and tests run on a PC too.

How a build works

 Eiffel --gec--> C --NDK clang--> one .so per processor type
                                      |
                 aapt2 + aapt --> APK --> zipalign (16 KB pages) --> apksigner

gec runs with --cc=no --finalize. A C file whose hash hasn't changed isn't recompiled. No compiler change was needed: gec's C compiled for Android as it stands.

Design decisions

Eiffel owns the loop

There are no callbacks into Eiffel. Android's events wait in a queue, and the app pulls them with wait_for_event or poll_event. A screen with a window and a lifecycle with a window always agree, because one command is applied per poll.

The Back key is decided ahead of time

With no callbacks, the app can't answer "did you handle this?" when Back arrives. So it sets a policy first.

Self-drawn UI

Apps draw their own pixels and hand them over with present_argb. Java stays out of the way: a small fixed helper is there only for what Android offers nowhere else.

Java answers through a mailbox

Read-aloud and the file picker answer on Java's own threads, and no Java thread may touch an Eiffel object. So EifPhoneActivity hands each answer to a small locked mailbox in the C glue, and wakes the Eiffel loop. The next wait moves it into the ordinary event queue. Text crosses as UTF-8 bytes, so Hebrew is safe.

A fast setjmp

On Android, setjmp saves the signal mask, which is a system call. gec's C uses it in every assertion block and rescue. runtime/c/sephone_fastjmp.h maps it to _setjmp for every phone build.

One Eiffel system per process

Android can start a new activity in a process while the old one is ending. A second Eiffel system would overwrite the first one's state and abort in the garbage collector. So the first main claims the process. A later one waits up to 2 seconds, then ends the process, and Android starts the app fresh.

Clean process end

The app ends with fflush and _exit, not exit, because exit handlers can race Android's own threads.

Release passwords

A release password reaches apksigner only through an environment variable. The contracts on EIFPHONE_KEYSTORE forbid every other route.
